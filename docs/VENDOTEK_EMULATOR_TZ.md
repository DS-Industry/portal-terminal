# Техническое задание: эмулятор терминала Vendotek

## 1. Цель

Разработать независимый эмулятор платёжного терминала Vendotek для разработки и тестирования ПО без физического устройства.

Эмулятор должен:
- принимать TCP-команды в том же протоколе, что и реальное устройство;
- корректно отвечать на полный цикл оплаты и отмены операции;
- позволять через UI выбирать режим поведения (успех, ошибка, задержка, потеря связи и т.д.) без перезапуска;
- поставляться как отдельный Docker-контейнер.

---

## 2. Область применения

| Входит в объём | Не входит |
| --- | --- |
| TCP-сервер протокола Vendotek | Полная копия всех полей официальной спецификации Vendotek |
| UI управления режимами | Авторизация UI |
| Лог последних операций в UI | Частичная оплата / другая одобренная сумма |
| Docker-образ и запуск на порту | Использование в production |
| Совместимость с описанным ниже протоколом | Множественные одновременные клиенты |

---

## 3. Архитектура

### 3.1. Компоненты

1. **TCP Protocol Server** — слушает порт, принимает кадры протокола Vendotek, формирует ответы согласно текущему режиму.
2. **Scenario Controller** — хранит активный режим и параметры (задержка в секундах). Режим действует до явной смены в UI.
3. **UI (обычное веб-приложение)** — выбор режима, параметры, статус, лог обменов. Авторизация не требуется.
4. **Docker-контейнер** — один независимый образ; TCP-протокол и UI могут работать в одном процессе/контейнере — способ не принципиален.

### 3.2. Порты (рекомендация)

| Порт | Назначение | Настраиваемость |
| --- | --- | --- |
| `4001` (по умолчанию) | TCP протокол Vendotek | через переменную окружения / аргумент |
| `8080` (по умолчанию) | HTTP UI | через переменную окружения / аргумент |

Точные значения портов не жёстко зафиксированы: должны задаваться при запуске.

### 3.3. Клиентский цикл оплаты (эталон)

Типичный цикл оплаты внешней системы:

1. TCP connect  
2. `IDL` → ответ  
3. `VRP` (сумма) → ответ с одобренной суммой  
4. клиент сверяет одобренную сумму с запрошенной  
5. `FIN` → ответ  
6. `IDL` → ответ  
7. TCP disconnect  

Отмена операции: `ABR` после установления соединения.

Эмулятор обслуживает **одно** активное TCP-подключение. Новые подключения после завершения предыдущего — допустимы (последовательные платежи).

## 4. Протокол

### 4.1. Кадр

**Запрос клиента → эмулятор:**

```
[length: 2 байта, big-endian][0x96][0xFB][TLV...]
```

`length` — длина тела после двухбайтового поля длины (включая `0x96 0xFB` и TLV).

**Ответ эмулятора → клиент:**

```
[length: 2 байта, big-endian][0x97][0xFB][TLV...]
```

### 4.2. TLV

Формат поля:

```
[param_id: 1 байт][param_len: 1 байт][param_data: param_len байт]
```

Поля, обязательные для совместимости с типовым клиентом:

| ID | Имя | Описание |
| --- | --- | --- |
| `0x01` | MessageName | ASCII: `IDL`, `VRP`, `FIN`, `ABR` |
| `0x03` | OperationNumber | ASCII-номер операции |
| `0x04` | Amount / ApprovedAmount | ASCII, сумма в копейках |
| `0x06` | Timeout | ASCII (опционально) |
| `0x08` | EventNumber | ASCII (опционально) |
| `0x11` | LocalTime | ASCII (опционально) |

Дополнительные TLV в ответах допускаются по усмотрению, если не нарушают разбор ответа клиентом.

### 4.3. Команды

#### IDL

Клиент отправляет:

- `0x01` = `IDL`

Эмулятор в режиме успеха отвечает минимум:

- `0x01` = `IDL`
- `0x03` = текущий operation number (ASCII)
- опционально `0x11` = локальное время

Типовой клиент берёт `operation_number` из ответа IDL и для следующей операции VRP использует значение `int(operation_number) + 1`.

#### VRP

Клиент отправляет:

- `0x01` = `VRP`
- `0x04` = сумма в копейках (ASCII; для суммы в рублях — `amount * 100`)
- `0x03` = номер операции

Эмулятор в режиме успеха отвечает:

- `0x01` = `VRP`
- `0x03` = operation number
- `0x04` = одобренная сумма в копейках (**равна запрошенной**)
- опционально `0x06` = timeout

Отказ для сценария ошибки: `0x04` = `0` (клиент сравнит одобренную сумму с запрошенной и зафиксирует ошибку).

#### FIN

Клиент отправляет:

- `0x01` = `FIN`
- `0x04` = сумма в копейках
- `0x03` = номер операции

Эмулятор в режиме успеха отвечает:

- `0x01` = `FIN`
- `0x03` = operation number
- `0x04` = сумма

После успешного FIN номер операции увеличивается.

#### ABR

Клиент отправляет:

- `0x01` = `ABR`

Эмулятор в режиме успеха отвечает:

- `0x01` = `ABR`
- `0x03` = operation number  

Состояние текущей оплаты сбрасывается.

### 4.4. Неизвестные команды

Логировать; ответ не отправлять или вернуть безопасный отказ — на усмотрение, главное — не уронить сервер.

## 5. Режимы поведения (сценарии)

Режим выбирается в UI и действует **постоянно**, пока пользователь не сменит его.

| Код режима | Название | Поведение |
| --- | --- | --- |
| `SUCCESS` | Успешная оплата | Корректные ответы на IDL / VRP / FIN / ABR; VRP возвращает запрошенную сумму |
| `REJECT` | Ошибка оплаты | На VRP возвращать одобренную сумму `0`; соединение не рвать |
| `DELAY` | Задержка | Перед ответом на **любой** шаг (IDL, VRP, FIN, ABR) ждать N секунд, затем отвечать по логике `SUCCESS` |
| `NO_RESPONSE` | Нет ответа | Принимать соединение и кадры, **не отправлять** ответ (клиент ждёт до своего socket timeout) |
| `DISCONNECT` | Потеря связи | При получении команды (или на выбранном шаге) **закрыть TCP-соединение** без ответа |

### 5.1. Параметры режимов

| Параметр | Для режимов | Описание |
| --- | --- | --- |
| `delay_seconds` | `DELAY` | Задержка ответа, сек. По умолчанию `3`, минимум `0`, максимум например `120` |
| `disconnect_on` | `DISCONNECT` | Опционально: на какой команде рвать (`ANY` / `IDL` / `VRP` / `FIN` / `ABR`). По умолчанию `ANY` (первый же запрос) |
| `no_response_on` | `NO_RESPONSE` | Опционально: на какой команде молчать. По умолчанию `ANY` |

### 5.2. Смена режима

- Через UI без перезапуска контейнера.
- Новый режим применяется к **следующим** обрабатываемым сообщениям; текущую уже начатую задержку можно не прерывать (допустимо).

## 6. UI

### 6.1. Требования

- Обычное веб-приложение (страница в браузере).
- Без авторизации.
- Доступ по HTTP-порту контейнера.

### 6.2. Функции экрана

1. **Выбор режима** — один активный режим из списка (§5).
2. **Параметры** — `delay_seconds`, при необходимости `disconnect_on` / `no_response_on`.
3. **Статус** — слушает ли TCP-порт; активен ли клиент; текущий режим; текущий operation number; сумма в процессе (если есть).
4. **Лог обменов** — последние N записей (например 50–100):
   - время;
   - направление (in/out);
   - тип сообщения;
   - сумма (если есть);
   - краткий результат / действие режима (delay, disconnect, no reply);
   - при ошибке — текст.

Допускается простой polling UI → backend каждые 1–2 сек или WebSocket — на усмотрение реализации.

### 6.3. API для UI (рекомендация)

Внутренний API только для UI. Пример:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/status` | Режим, параметры, TCP-статус |
| `POST` | `/api/mode` | Установка режима и параметров |
| `GET` | `/api/logs` | Последние записи лога |
| `POST` | `/api/logs/clear` | Очистка лога (опционально) |

## 7. Docker

### 7.1. Требования

- Отдельный независимый контейнер.
- Проброс портов: TCP протокола и HTTP UI.
- Переменные окружения, например:
  - `VENDOTEK_TCP_HOST=0.0.0.0`
  - `VENDOTEK_TCP_PORT=4001`
  - `UI_HOST=0.0.0.0`
  - `UI_PORT=8080`
  - `DEFAULT_MODE=SUCCESS`
  - `DEFAULT_DELAY_SECONDS=3`

### 7.2. Пример запуска

```bash
docker build -t vendotek-emulator .
docker run --rm -p 4001:4001 -p 8080:8080 vendotek-emulator
```

Внешняя система подключается к IP хоста/сервиса эмулятора и TCP-порту протокола.

## 8. Критерии приёмки

1. Контейнер поднимается, TCP и UI доступны с хоста.
2. При режиме `SUCCESS` полный цикл `IDL → VRP → FIN → IDL` завершается успешно: одобренная сумма равна запрошенной.
3. При режиме `REJECT` цикл оплаты завершается отказом (одобренная сумма не совпадает / равна нулю).
4. При режиме `DELAY` ответы приходят с задержкой ~`delay_seconds` на каждом шаге; при достаточном timeout клиента оплата всё ещё может успешно завершиться.
5. При режиме `NO_RESPONSE` клиент получает таймаут / отсутствие ответа.
6. При режиме `DISCONNECT` клиент получает ошибку связи (сокет закрыт).
7. Смена режима в UI без перезапуска контейнера меняет поведение следующих операций.
8. `ABR` в режиме `SUCCESS` отрабатывает без падения эмулятора.
9. Эмулятор не падает при некорректном/коротком кадре.
10. В UI виден лог хотя бы последних обменов.

## 11. Эталон совместимости

Минимально необходимая совместимость определяется разделом 4 настоящего ТЗ:

- заголовок запроса: `0x96 0xFB`
- заголовок ответа: `0x97 0xFB`
- сумма всегда в **копейках**, ASCII, в TLV `0x04`
- команды: `IDL`, `VRP`, `FIN`, `ABR`

Дампов реального железа нет — расширять протокол сверх описанного цикла не требуется.
